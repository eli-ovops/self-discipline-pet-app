## 一、总体评估

**架构核心设计是正确且克制的**：三层证据分离（命令/本地状态/系统观察）、App Group 单写入者协议、纯状态机与副作用协调器分离、通知不做状态权威、真机证据唯一门禁——这五项抓住了"Apple 无 Shield 真值回调"这一核心约束，方向对。

**但发现两类问题：**

1. **版本漂移（最严重）：** 架构基于 PRD v0.1.4，未同步 v0.1.5 的 6 项变更，其中 3 项直接要求架构新增验证项或字段（R1）；
2. **三个真实技术盲点：** 通行窗口起点的确认信号与 PRD 口径不一致（R2）、重锁生效延迟的产品语义未定义（R3）、打开主 App 失败路径与 fallback 政策未决（R5）。

## 二、第一性原理审查：架构是否忠于根目标

### 2.1 确认正确的设计（建议保留）

| 设计 | 判断 |
|---|---|
| 三层证据分离（§17.1） | ✅ 最硬的设计。准确识别"App 没有通用可靠的 Shield 真值回调"，拒绝把命令层/本地层自动升级为系统观察层 |
| App Group 单写入者协议（§9.2） | ✅ 每类记录唯一写入者 + generation/recordID/sequence 对账，正确处理了"App Group 是运输层不是事务数据库" |
| 纯状态机 + 副作用协调器分离（§6.3/8.2） | ✅ Reducer 只接收注入时间与命令结果，输出 Effect，避免被系统 API/真实时间污染测试 |
| 通知不做状态权威（§11） | ✅ 60 分钟截止以持久化时间戳为逻辑权威，每次入口先 reconciliation，正确 |
| `stopMonitoring` 不用于解除 Shield（§10.2） | ✅ 技术上正确：解除 = 清 `ManagedSettingsStore.shield`（无完成回调），停止监控计划是另一回事 |
| Monitor 仅作辅助证据（§10.5） | ✅ 没有夸大 DeviceActivityMonitor 的角色 |
| 不创建 Report Extension / 无第三方依赖 / P0 无 URL scheme | ✅ 范围克制，符合 P0 门禁 |

### 2.2 第一性原理层面的一个矛盾

架构自己承认"App 没有通用可靠的 Shield 真值回调"（§5/§17.1），**但同一约束反向要求"解除/重锁的确认信号"必须提前定义清楚**——架构 §10.2 说"不假设存在可靠的解除完成回调"，可 PRD v0.1.5 却把通行窗口起点写成"`stopMonitoring` completion 成功时刻"（基于"解除=停止监控"的错误假设）。两个文档各写了一半事实，P0 实现时会打架（见 R2）。约束没有贯穿到所有依赖该约束的定义里。

## 三、对抗式审查发现（按严重度）

### 🔴 R1. 架构基于 PRD v0.1.4，未同步 v0.1.5 的 6 项变更

| v0.1.5 条款 | 架构现状 | 需要的修改 |
|---|---|---|
| §8.5-20 重锁生效延迟专项（0s/30s/1min/5min 实测） | 无对应验证项 | P0 证据矩阵新增 |
| §8.5-21 连续申请专项（新窗口+累计通行时长+无重复奖励） | §15.1-3 写"申请后进入**同一**通行窗口"——措辞与 v0.1.5"每次申请独立窗口+累计通行时长累加"冲突 | 修正测试语义 + snapshot 增加累计通行时长字段 |
| §8.5-3 Shield 展示/直接返回**可记录性验证** | §12.2 直接写"不记录"——但 v0.1.5 要求 P0 **验证是否可记录并给出结论**（北极星可测性） | 证据矩阵加可记录性验收项 |
| §9.3 累计通行时长字段 | snapshot 无此字段 | Shared DTO + 本地数据补字段 |
| §4.2 通知关闭时申请页提示"主动回到 App 返回" | 未体现（UI 层，低优先级） | 文案键 |
| §8.5-4 冷启动申请路径 | §7.2 步骤 3-5 已覆盖 | ✅ 已覆盖 |

**直接冲突项：** §15.1-3"申请后进入同一通行窗口"若按字面实现，会违反 v0.1.5"每次申请开启独立 60 分钟窗口 + 累计通行时长累加"的决策（该决策是为对抗"无限续杯"而新增）。

### 🔴 R2. 通行窗口起点的确认信号：PRD 与架构口径不一致

- **v0.1.5 §8.3/§4.4：** 起点 = `stopMonitoring` completion 成功时刻；
- **架构 §10.2：** "P0 不把 stopMonitoring 当成解除 Shield 的方法"——解除 = 清 `ManagedSettingsStore.shield`，而该 API **无完成回调**。

事实是：

- 解除 = 清 `ManagedSettingsStore.shield`（无回调，只能本地记录命令发出时刻）；
- `stopMonitoring` 的 completion 只能证明"监控计划停止被系统接受"，不能证明 Shield 已消失；
- "系统确认解除成功"（PRD 用语）在 API 层**不存在**，只能人工观察（三层证据第 3 层）。

**决策（D1，已拍板）：** 修订 PRD v0.1.5 —— 窗口起点 = "解除命令被本地确认无异常的时刻"（ManagedSettings 无回调，以命令发出为准），并注明真实 Shield 消失以真机观察为准、存在秒级至分钟级的传播延迟。

### 🔴 R3. 重锁生效延迟的产品语义未定义

`ManagedSettingsStore` 写入生效是异步传播的（秒级到分钟级）。用户返回 → 重锁命令发出 → 恢复专注计时——**但用户如果立刻点开刚解除的 App，Shield 可能尚未恢复**，存在真实暴露窗口。这正是 v0.1.5 §2.3/§8.5-20 要求实测并设阈值（>2 分钟入 FAIL 边缘评审）的原因。

架构 §8.4 以"命令成功+本地记录"恢复计时（产品语义），真机阶段人工观察延迟（证据语义）——**方向正确，但没有引用 v0.1.5 的 FAIL 判据**。需要：① 架构显式引用"重锁生效延迟 > 阈值 → FAIL 边缘评审"；② P0 矩阵补"解除传播延迟"（提交申请 → Shield 消失）实测——用户提交申请后立刻点受限 App 可能再撞一次 Shield。

### 🟠 R4. "返回专注"按钮的归属未定义——直接决定"直接返回可观测性"

| 实现 | 可观测性 | 与 PRD 关系 |
|---|---|---|
| 系统默认关闭按钮（重命名 closeButtonTitle） | 不可观测（点击不经产品代码） | 符合 v0.1.5"直接返回不可观测"结论，零工作 |
| 自定义"返回专注"按钮（触发 ShieldAction） | **可观测** | 能补上 v0.1.5 的测量缺口，但需要实现动作处理 + 改变用户操作语义 |

**决策状态：D2 待用户拍板**（系统按钮 vs 自定义按钮）。

### 🟠 R5. 打开主 App 的失败路径 + fallback 政策未决

1. **失败路径缺失：** 用户点"申请使用"→ 官方打开能力未生效（用户留在原地）→ 没有 fallback 说明。用户会被卡在"申请了但没跳转"的困惑中。至少需要 Shield 配置文案"若未自动跳转，请手动打开《自律宠物》完成申请"，或 P0 明确该场景的判定；
2. **排除 URL scheme 与 PRD 冲突：** PRD v0.1.5 §4.4 允许"Apple 官方能力范围内的替代导航"。URL scheme 是官方公开能力，且是唯一**不需要服务器/域名托管**的打开方式（Universal Link 需要 AASA 托管，P0 无服务器）。架构同时排除两者后，若官方打开能力不可用，P0 将直接 FAIL——需要用户在 P0 前明确：官方打开能力 FAIL 时是直接 FAIL，还是允许 URL scheme fallback。

**决策状态：D3 待用户拍板。**

### 🟠 R6. 申请页取消路径未定义

状态机（§8.1）只有 `ACCESS_REQUESTED → ACCESS_WINDOW_ACTIVE`（提交后），**没有"用户进入申请页但不提交、直接退出"的迁移**。该场景下：pending intent 已被消费、Shield 应保持、专注应继续、无副作用。若实现时漏掉，可能出现"打开过申请页就算申请过"的错误。需显式迁移：`ACCESS_REQUESTED →(取消)→ FOCUSING`（Shield 保持，无奖励影响）。

### 🟡 R7. 状态机图与 PRD 产品状态映射不完整

架构把 `SHIELD_PRESENTED`、`REQUESTING_USE` 合并为 `ACCESS_REQUESTED`，把 `COMPLETED_NO_REQUEST` / `COMPLETED_WITH_REQUEST` 合并为 `COMPLETED`（eligibility 转入 `RewardEligibility` 字段）。可接受，但建议补一张映射表：`COMPLETED` + `RewardEligibility.noRequestBonus` 等，防止"无申请加分"语义在实现中丢失。

### 🟡 R8. 解除传播延迟未显式列入 P0 矩阵

同 R3：提交申请 → 解除命令发出 → Shield 实际消失之间有延迟。用户若在延迟窗口内点受限 App，会再次撞上 Shield。建议 P0 矩阵记录该延迟（与重锁延迟对称）。

### 🟡 R9. UserDefaults 跨进程可见性应列为 P0 前置 spike

§9.4 已预留"实测不满足再评估文件容器"——正确。但建议把"App Group UserDefaults 跨进程写读可见性"列为**核心闭环之前的第一个 spike**（Simulator + 真机各一次），而不是等闭环失败才回头看。已知事实：App Group UserDefaults 跨进程共享是 Apple 官方支持的标准做法，但变更通知不跨进程、读取方需重新读取；实践中偶有可见性延迟。

### 🟡 R10. 加速测试模式的边界确认

§17.3 的 10s/30s/60s 加速模式方向正确，补充确认三点：① 必须 Debug-only 且与 Release 字段分离，防止测试数据混入真实 deadline；② 缩放应同时作用于 deadline 计算与通知 trigger；③ 真实 10/30/60 分钟至少一次全流程真机验证（文档已有此要求，确认保留）。

### 🟡 R11. 日志隐私检查点

§12.3 脱敏设计正确，但开发期 OSLog 是最容易泄漏 token/原因正文的地方（§18 红队表已自认"仍需代码审查检查 OSLog 参数"）。建议把"日志 grep 检查（原始 Token、自定义原因、账号信息）"固化为 P0 验收清单项，而不是依赖自觉。

### 🟡 R12. 临时豁免扩展点（提示性）

PRD §4.2-5 的"当前会话临时豁免"是 P1 功能，P0 不含——架构 Domain 无对应。建议在 `ActivitySelection` 模型上留注释/扩展点（豁免 = 构建 selection 时排除），避免 P1 重构。

### 🟡 R13. 文档交叉引用更新

- 头部"对应权威产品文档 v0.1.4"→ v0.1.5；
- §21.3 的 `openParentalControlsApp`：建议把该 API 的 spike 提到 P0 开发顺序第 1 步（§19 目前排在第 6 步），因为它是申请闭环的咽喉——先确认它存在、可调用、能打开主 App，再谈后续。
