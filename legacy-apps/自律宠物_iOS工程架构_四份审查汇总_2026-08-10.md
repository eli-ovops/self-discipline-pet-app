四份报告对架构主体的判断高度一致：

- 四产品 Target + 一测试 Target 合理；
- 纯状态机与副作用分离合理；

- 核心风险仍是 Apple 能力和真机行为，而不是 SwiftUI 页面搭建。

综合判断：

> **架构主体保留，但在开工前应形成 v1.1 小修订。建议采纳 11 项、拒绝 7 项、后置 6 项。不要根据四份报告直接全面开工。**

1. 把 P0 拆成更早止损的连续 Spike；

4. 保持 `openParentalControlsApp` 为官方首选，不引入未经证明的 URL Scheme fallback；
5. 继续以 PRD v0.1.4 为唯一权威，v0.1.5 仍是待复验草稿。

## 4. Apple API 事实核验

### 4.1 `openParentalControlsApp` 确实存在

本机 iPhoneOS 26.5 SDK 明确定义：

```swift
@available(iOS 26.5, *)
case openParentalControlsApp
```

它属于 `ManagedSettings.ShieldActionResponse`。

Apple 官方描述是：

> An instruction for the system to open your parental controls app that is responsible for shielding the application or web browser.

官方文档：[ShieldActionResponse.openParentalControlsApp](https://developer.apple.com/documentation/managedsettings/shieldactionresponse/openparentalcontrolsapp)

因此：

- 报告 2 所称“公开 API 不存在”是错误；
- 报告 2 所称“它只打开系统设置中的家长控制页面”与 Apple 官方描述不符；
- 架构 v1.0 选择该 API 作为 iOS 27 真机首选路径是合理的；
- 但编译期存在不等于目标真机体验必然稳定，仍必须作为 P0-A 最早的真机 Spike。

### 4.2 不应现在加入 URL Scheme fallback

四份报告中两份建议必须加入 URL Scheme。当前不采纳，原因：

1. Apple 已提供专门的 `ShieldActionResponse.openParentalControlsApp`；
2. P0 的目的正是验证官方 Shield 路径是否成立；
3. URL Scheme 会增加伪造入口、防重放、Extension 可调用性和审核语义风险；
4. 用另一条路径证明后半段可运行，不能证明目标 Shield 闭环成立；
5. 当前 PRD 已允许官方能力范围内的替代导航，但不允许静默绕过核心失败。

建议口径：

> P0 先验证 `openParentalControlsApp`。若真机无法形成可理解路径，记录 FAIL 并回到架构评审；不自动启用 URL Scheme。

### 4.3 Shield Configuration 字段并非全部必填

本机 ManagedSettingsUI SDK 中 `icon`、`title`、`primaryButtonLabel` 等均为 Optional，初始化参数也有 `nil` 默认值。

因此报告 2 所称“icon、title、primaryButtonLabel 必须提供”不准确。

但从可理解性出发，P0 仍应提供：

- 最小可识别 App 图标或占位标识；
- 清楚标题；
- “申请使用”与“返回”按钮文案；
- 不伪装系统错误的说明。

这属于最小 P0 体验资产，不等于制作正式猫、狗、兔资产。

四份报告共同或交叉指出：

1. Shield 打开主 App 必须最早真机验证；
2. App Group 跨进程可见性必须尽早验证；

## 6. 建议采纳的 11 项修改

### A1. 将 P0 拆成三个连续门禁

不改变总范围，只改变顺序：

**P0-A：Apple Capability Spike**

- entitlement/签名可运行性；
- Family Controls 授权与选择；
- Shield 施加；
- Shield Action → `openParentalControlsApp`；
- 完整集合解除；
- 完整集合重新施加；
- App Group Extension 写、主 App 读。

任一核心项失败，先停止，不继续通知和完整状态机 UI。

**P0-B：闭环集成**

- 申请页；
- 原目标、范围、原因；
- 10/30/60 时间戳和本地通知；
- 返回、放弃、60 分钟超时；
- 最小诊断页。

**P0-C：恢复与红队矩阵**

- 冷启动；
- 强制终止后恢复；
- 撤权；
- 重复点击；
- 旧 intent；
- 通知关闭；
- 解除/重锁传播延迟；
- 其他 Screen Time App 并存。

### A2. App Group 可见性前置 Spike

在 P0-A 验证：

1. Shield Action 写入 unique intent；
2. 系统打开主 App；
3. 主 App 冷启动立即重新读取；
4. 记录读取延迟、丢失、重复和旧值；
5. 至少覆盖连续快速点击和 Extension 快速结束。

P0 仍先用 UserDefaults，不预先迁移数据库。

### A3. 强制增加冷启动与被杀恢复

真机矩阵新增：

- `ACCESS_WINDOW_ACTIVE` 时上滑终止主 App；
- 等待后从通知或手动打开；
- 恢复 sessionID、generation、开始时间、deadline 和剩余状态；
- 不错误回到 IDLE；
- 60 分钟已到则校正为 `ACCESS_TIMED_OUT`；
- 重新打开受限 App，人工观察 Shield 实际状态。

### A4. 增加授权丢失事件

Domain 增加：

```text
SessionEvent.authorizationChanged
SessionEvent.authorizationRevoked
```

每次 App 激活和关键 ManagedSettings 操作失败时重新核验授权。

失权后：

- 不显示保护成功；
- 停止继续承诺重锁；
- 进入 `RECOVERY_REQUIRED`；
- 清理或封存本地会话状态；
- 提示用户重新授权或结束会话。

不使用不可关闭的永久 Alert；必须保留退出和删除数据路径。

### A5. 定义 `ProductError` 分类

最少分为：

- `transient`：可有限重试；
- `authorizationRequired`：需要用户授权；
- `entitlementUnavailable`：P0 阻断；
- `systemLimitation`：公开 API 不支持目标；
- `storageCorrupted`：拒绝不可信 snapshot 并进入恢复；
- `invariantViolation`：状态机不变量破坏，停止副作用；
- `unknown`：记录脱敏信息，不伪装成功。

每类定义用户可见行为、是否重试、是否结束会话和证据字段。

### A6. 增加申请取消迁移

状态机补充：

```text
ACCESS_REQUESTED
  → 用户取消
  → FOCUSING
```

规则：

- Shield 保持；
- 不计正式申请；
- 不影响奖励；
- pending intent 保持已消费，避免重复导航；
- 不触发解除和通知。

### A7. 增加状态映射表

明确产品状态与内部字段关系，例如：

- `COMPLETED + requestedAccess == false` → 基础奖励 + 无申请加分；
- `COMPLETED + requestedAccess == true` → 基础奖励，无无申请加分；
- `ACCESS_TIMED_OUT` → 无奖励，保持解除；
- `ABANDONED` → 无奖励，立即解除；
- `RECOVERY_REQUIRED` → 不显示正在保护。

### A8. 传播延迟双向专项

真机分别记录：

- 申请后 Shield 消失延迟；
- 返回后 Shield 恢复延迟。

测试点建议：0 秒、30 秒、1 分钟、5 分钟。

架构只记录命令时间和首次人工观察时间，不自行声称系统完成。

具体 FAIL 阈值在第一次真机数据后冻结，不在架构里凭空写死。

### A9. 超时保持解除的幂等恢复

不改变当前 PRD 的产品决定。

在 `ACCESS_TIMED_OUT` reconciliation 中：

- 取消提醒；
- 不重锁；
- 必要时幂等地再次请求清除本次选择集合的 Shield；
- 记录命令层结果；
- 真机人工观察真实状态；
- UI 不声称系统已经解除。

这解决“产品要求保持解除，但系统真实状态未知”的矛盾。

### A10. 收紧加速测试证据口径

- 仅 `#if DEBUG`；
- 测试配置不进入 Release；
- deadline 和 notification trigger 使用同一测试时钟配置；
- 加速模式只用于 UI、Reducer 和快速集成；
- 任何加速模式结果不能计入 P0 核心 PASS；
- 至少一次完整真实 10/30/60 分钟真机流程。

### A11. 开工时补 Git 与证据规则

这不是架构重构，但属于 Kickoff 必需项：

- 本地 Git 是否初始化；
- `.gitignore`；
- `xcuserdata/`、DerivedData、大型录屏排除；
- xcconfig 中不得出现 secret；
- 证据文件名包含日期、测试编号、设备、结果；
- 大型证据不直接纳入 Git；
- GitHub 上传仍需另行授权。

## 7. 明确不采纳的 7 项建议

### N1. 不把 `openParentalControlsApp` 判定为不存在

已被本机 SDK 和 Apple 官方文档反证。

### N2. 不在 P0 预先增加 URL Scheme fallback

先验证 Apple 专用响应；失败则回评审，不用另一条路径掩盖核心失败。

### N3. 不预先迁移 SQLite、WAL、SwiftData 或 FileCoordinator

UserDefaults 是 P0 的可证伪候选。先实测，再按证据升级，避免同时验证两套存储。

### N4. 不把 Shield 图标等字段说成 API 必填

SDK 中字段是 Optional；但保留最小可理解 UI。

### N5. 不把 60 分钟超时改成自动重锁

这是产品决策，不是架构师可自行改写。当前权威 PRD 明确保持解除。

### N6. 不添加放弃后的冷静期

当前 PRD 已明确暂不设置，先记录行为。没有真实数据前不加惩罚。

### N7. 不增加代码层 `Experiments/` 模块

宠物增量价值和留存应由独立行为验证方案回答，不应伪装成 P0 技术模块。

## 8. 后置而非删除的 6 项

### D1. 宠物是否真正提高复用

重要，但不属于 P0 工程架构 PASS。应在 P0 并行准备非开发对照测试。

### D2. Day 7、Day 30 与付费指标

属于行为验证和商业化协议，不能用技术 Spike 证明。

### D3. 正式宠物资产和 Shield 美术

P0 只需最小可识别占位；正式三宠资产继续受视觉和行为门禁约束。

### D4. SessionCoordinator 是否进一步拆分

当前已有 Reducer、Client 和 Coordinator 分层。先保持最小；若实现中 Coordinator 开始持有大量诊断或存储细节，再拆 `DiagnosticsCollector` / `EffectExecutor`。

### D5. Bundle ID 中性化

当前 ID 已由用户确认并适合 P0。未来转让、公司主体或正式品牌变化时另行迁移评审。

### D6. 精确 Screen Time 报表

P0 不引入 Report Extension，不记录各 App 前台时长；后续只有真实行为验证需要时再评估。

## 11. 最终判断
